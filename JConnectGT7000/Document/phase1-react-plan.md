# Phase 1 — ย้าย Frontend จาก PHP ไป React

**พักงาน React แล้ว (6 ต.ค. 2026)** ห้ามเรียก `phase1-lead`, `feature-builder`, `backend-builder`, `webapp-builder`, `phase1-verifier` หรือ `php-mapper` จนกว่าผู้ใช้จะสั่งให้ทำ React ต่อ งานช่วงนี้คือเพิ่มฟังก์ชันบน PHP ในโฟลเดอร์ `frontend` คลื่นที่ accept ไว้แล้วยังคงอยู่ คลื่น 16–17 เป็น return และคลื่น 18–19 ยังไม่มี PO

เอกสารนี้คือข้อตัดสินของ Phase 1 ตัว agent ใน `.cursor/agents/` ต้องทำตามไฟล์นี้เมื่อกลับมาทำ React งาน 3D, asset management และ site management เป็น Phase 2 ยังไม่เริ่มในเฟสนี้

โฟลเดอร์ใหม่สองอัน:

| โฟลเดอร์ | หน้าที่ |
|---|---|
| `webapp` | React SPA ที่จะแทนหน้า PHP |
| `backend` | API ของแอป ที่จะแทน controller ของ CodeIgniter |

PHP ที่พอร์ต 80, `dataedge`, `alarm-engine` และ TimescaleDB ยังทำงานต่อระหว่างย้าย ผู้ใช้ชุดเดิมในตาราง `ia_users` ต้องล็อกอินแอปใหม่ได้โดยไม่รีเซ็ตรหัสผ่าน

## สถาปัตยกรรม

```
เบราว์เซอร์
  └─ webapp (Vite, พอร์ต 5173 ระหว่างพัฒนา)
       └─ /api/v1  →  backend (Fastify, พอร์ต 4000)
                        └─ PostgreSQL / TimescaleDB  ฐาน jconnect
dataedge และ alarm-engine ยังเป็นบริการแยก
PHP CodeIgniter ยังเสิร์ฟของเดิมจนกว่าหน้านั้นจะเทียบเท่า
```

`backend` เป็น API ของหน้าจอและการจัดการข้อมูลแอป ไม่อ่าน Modbus, BACnet, SNMP หรือ MQTT เอง งานโปรโตคอลอยู่ที่ `dataedge` งานส่งการแจ้งเตือนอยู่ที่ `alarm-engine` เมื่อถึงโมดูลที่ต้องคุยกับสองบริการนี้ ให้เรียก HTTP ที่มีอยู่แล้ว

### การเปลี่ยนฐานข้อมูล

เพิ่มฟิลด์หรือตารางได้ จุดตั้งต้นคือฐานเวอร์ชันเดิมจาก `Database/jconnect_2026-10-05.sql` เมื่อจะอัปเดตซอฟต์แวร์ PHP เดิม ให้รัน seed ชุดเดียวกันนี้ทับฐานนั้นได้ และ PHP ต้องยังล็อกอิน อ่าน และเขียนข้อมูลเดิมได้

ไฟล์อยู่ที่ `Database/migrations/` ชื่อ `001_คำอธิบายสั้น.sql` เรียงตามเลข ตัวรันบันทึกไฟล์ที่ใส่แล้วลงตาราง `schema_migrations` รันซ้ำแล้วข้ามไฟล์ที่ใส่แล้ว

กติกาของทุกไฟล์:

- ใช้ `CREATE TABLE IF NOT EXISTS` และ `ADD COLUMN IF NOT EXISTS`
- คอลัมน์ใหม่บนตารางเดิมต้องเป็น `NULL` ได้ หรือมี `DEFAULT` เพื่อให้ `INSERT` ของ PHP ที่ไม่ส่งคอลัมน์นั้นยังผ่าน
- ห้าม `DROP`, `RENAME` หรือเปลี่ยนชนิดคอลัมน์ที่ PHP, `dataedge` หรือ `alarm-engine` ใช้อยู่
- ห้ามทำให้คอลัมน์เดิมเป็น `NOT NULL` ถ้าของเดิมรับค่าว่าง
- ข้อมูลตั้งต้นที่แอปใหม่ต้องการอยู่ในไฟล์ migration เดียวกัน ไม่แยกสคริปต์คนละชุด

คลื่น 0 สร้างตาราง `schema_migrations` กับคำสั่งรัน seed นี้ก่อนมีฟิลด์ธุรกิจใหม่

### สัญญา API

- พรีฟิกซ์ `/api/v1`
- JSON
- สำเร็จ: `{ "data": ... }`
- ผิดพลาด: `{ "error": { "code": "STRING_CODE", "message": "..." } }`
- ล็อกอิน `POST /api/v1/auth/login` ด้วยอีเมลและรหัสผ่านจาก `ia_users`
- access token อายุสั้นในหน่วยความจำของเบราว์เซอร์
- refresh token ในคุกกี้ `HttpOnly`, `SameSite=Lax`
- สิทธิ์อ่านจาก `ia_permission` และเมนูจาก `ia_menu` ไม่ได้สร้างระบบสิทธิ์ชุดใหม่

ระหว่างพัฒนา Vite proxy `/api` ไปที่ `http://localhost:4000` PHP ยังอยู่ที่พอร์ต 80

## มาตรฐานความเท่ากัน

React ถือว่าตรง PHP เมื่อครบทุกข้อนี้ในหน้านั้น:

- เมนูและลิงก์ไปหน้าเดียวกันมีครบ
- รายการ คอลัมน์ ตัวกรอง การเรียง และการแบ่งหน้าตรงกัน
- ฟอร์มมี label, ชื่อฟิลด์, ประเภทอินพุต, ค่าเริ่มต้น, required และตัวเลือก dropdown ครบทุกช่อง
- บันทึก แก้ไข ลบ แล้วย้อนอ่านค่าเดียวกันจากฐานข้อมูล
- ข้อความไทย/อังกฤษที่ใช้บนหน้านั้นมีครบ
- รูปภาพ โลโก้ ไอคอนเมนู ไอคอนปุ่ม และรูปอุปกรณ์หรือเทมเพลตที่หน้า PHP แสดง ต้องมีใน React ด้วย ที่มาไฟล์หรือ asset path เดียวกัน หรือแสดงผลเทียบเท่า
- ถ้าบริการภายนอกออฟไลน์ทั้งสองฝั่ง แสดงสถานะเดียวกันได้ แต่ UI ฟิลด์ รูป และไอคอนต้องมีครบ

## ลูปตรวจงาน

วนแบบนี้จนกว่าคลื่น 19 จะถูก accept และ `Document/nginx-switch-plan.md` ไม่มีรายการ Still on PHP ที่เป็นฟังก์ชัน Phase 1

1. `php-mapper` ลิสต์หน้า ฟังก์ชัน และฟิลด์ฟอร์มของคลื่นนั้นจาก PHP และแมปคลื่นถัดไปพร้อมกันเมื่อทำได้
2. สั่งโค้ดแบบขนานอย่างน้อยสองสาย: `backend-builder` กับ `webapp-builder` สำหรับคลื่นปัจจุบัน และ `feature-builder` สำหรับคลื่นถัดไปหรือรายการ gap คนละโมดูล
3. `phase1-verifier` ล็อกอินทั้ง PHP (`http://127.0.0.1/`) และ React (`http://127.0.0.1:5173/`) ด้วยชื่อ `Supperadmin` แล้วเทียบทีละหน้า ทีละฟังก์ชัน ทีละฟิลด์ฟอร์ม รวมถึงรูปภาพและไอคอน
4. ตัวตรวจเขียน PO ที่ `Document/po/wave-N.md` สรุปว่าแต่ละรายการตรงกัน ขาด หรือต่าง และเสนอ `accept` หรือ `return` ตัวตรวจไม่ปิดคลื่นเอง
5. `phase1-lead` อ่าน PO แล้วเขียนบรรทัด `Lead decision` รับคลื่นหรือส่งกลับเฉพาะจุดที่ยังไม่ตรง
6. ถ้า `return` ให้ `feature-builder` หรือคู่ builder แก้ แล้วตรวจใหม่ ถ้า `accept` จึงไปคลื่นที่ยังไม่จบ
